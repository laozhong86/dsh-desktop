# 数据迁移验证报告：旧壳 → Next 壳

> 验证日期：2026-10-26
> 目的：确认从 `dsh-plugin-desktop`（旧壳，当前出厂）切到 `dsh-desktop-next`（新壳，已品牌化）时，用户数据不会丢失
> 方法：直接比对两个壳在本机的真实数据目录（`~/.omnimux` 与 `~/.omnimux-dev`）

---

## 0. 结论

**迁移风险远低于预期。** 关键发现：两个壳用**不同的默认 profile 名**（旧壳 `omnimux` / 新壳 `desktop`），且数据格式完全兼容，所以不是"覆盖式迁移"，而是**增量并存**。

- 会话：格式完全一致，可无损搬运
- 设置：YAML 结构完全一致，可无损搬运
- 插件：旧壳 305 个依赖**全部被新壳包含**，零丢失
- 冲突风险：profile 名不同，不会互相破坏

## 6. 冲突风险分析

### 6.1 已排除的风险

- **profile 互相覆盖**：旧壳 `omnimux` vs 新壳 `desktop`，不同名，不会覆盖。
- **会话格式不兼容**：完全一致。
- **设置格式不兼容**：完全一致。
- **插件丢失**：零丢失。

### 6.2 仍需注意的风险

1. **`node_modules` 不能直接搬**：两边依赖数不同（305 vs 333），必须让新壳重新物化。直接复制 `node_modules` 会缺包。
2. **`~/.omnimux` 与 `~/.omnimux-dev` 是两套数据**：品牌化后新壳默认读 `~/.omnimux`（已改为与旧壳同目录），但当前本机的新壳仍用 `~/.omnimux-dev`（开发版行为）。**真正切壳时，新壳会直接读旧壳的 `~/.omnimux`** —— 这是好事，但也意味着两者会共享同一个目录，需要确认不会互相写坏。
3. **回退路径未验证**：切过去之后，旧壳还能不能正常启动，本轮没有实测。

---

## 7. 建议的切壳方案

基于以上发现，切壳可以分三步：

1. **备份**：切之前把 `~/.omnimux` 整体复制一份（473M 量级，成本低）。
2. **切壳**：让新壳读 `~/.omnimux`（品牌化已把默认值改成这个），让它按自己的 preset 重新物化 `node_modules`。
3. **验证**：启动新壳，确认会话列表、设置、插件都在。

**回退方案**：把备份目录换回去，旧壳照常启动。
