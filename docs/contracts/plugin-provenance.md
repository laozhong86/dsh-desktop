# Plugin provenance in a release

A release publishes `plugin-provenance.json` beside the installers. It records
the application commit, and for every plugin the lockfile pinned: its name, its
version, and the commit that version's tarball was built from.

## Why

The installer carries whatever plugin versions `yarn.lock` resolved at build
time. Nothing else said which ones those were, so answering "what code is in
this installer" meant re-reading a lockfile from a guessed commit, and finding
the matching plugin source meant searching a second repository for a version
label. The record answers it in one file, from the release itself.

The `commit` field is npm's `gitHead`: the commit the published tarball was
built from. That is the link between a shipped byte and a source revision —
which is why it is worth publishing even though it is `null` for some entries.

## Shape

```json
{
  "app": { "commit": "<40 hex>", "version": "2.0.19" },
  "plugins": [
    { "name": "omnimux", "version": "0.1.3", "commit": "<40 hex>" },
    { "name": "dsh-plugin-desktop", "version": "0.0.0-use.local", "commit": null, "source": "workspace" },
    { "name": "dsh-better-sidebar", "version": "0.28.1", "commit": null, "note": "registry reports no gitHead for this version" }
  ],
  "generatedAt": "2026-10-30T12:00:00.000Z"
}
```

`source: "workspace"` means this repository builds the package, so `app.commit`
covers it. `note` explains a `null` commit instead of failing the release: an
incomplete record is worse than a complete one, and far better than no release.

## Rules

- The file MUST be generated by `scripts/build-plugin-provenance.mjs`; do not
  hand-write it.
- A release MUST NOT publish without it. `release.yml` generates it before the
  GitHub Release step and lists it in `files`.
- A `null` commit is a fact to record, not an error to suppress. If a package
  gains a `gitHead`, the entry loses its `note` on the next release without any
  other change.
