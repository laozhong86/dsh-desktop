# OmniMux 社媒增长专家团：产品闭环提案

> 状态：已确认的产品方向；尚未实现。
> 范围：OmniMux Desktop 的增长垂直插件，以及它与现有执行能力的边界。
> 不包含：账号规避、未授权账号操作、无人审核的大规模发布。

## 要解决什么

OmniMux 现有能力已经能让 Agent 制作内容、管理已授权账号、发出内容并调用部分社媒数据能力。它们解决的是执行问题，但没有把一个产品从“我该怎样靠社媒获客”带到“我完成了一轮可复盘的增长实验”。

新增的增长专家团要补的是判断和学习：用户提供业务信息，专家团确定本轮目标、实验与内容方向，OmniMux 执行经过审核的分发，结果再回到下一轮判断。

对用户来说，产品是一段持续推进的对话；对系统来说，它是一组有版本、有证据、可协作的增长对象。

## 产品对象与闭环

```text
业务画像库
    ↓
增长方案卡（主目标）
    ↓
增长实验卡（可证伪的子目标）
    ↓
内容生产与审核
    ↓
分发执行与发布回执
    ↓
结果回读与复盘
    └──────────────── 回写业务画像与下一版方案
```

### 1. 业务画像库

通过对话或产品链接建立，并由用户与 Agent 随时修订。

稳定事实包括：产品、目标客户、痛点、需求、价值主张、价格、渠道和约束。

增长资产与稳定事实分开保存，包括：内容方向、内容母模板、历史实验、已验证表达、失败表达、账号表现和证据来源。一次内容实验不能反过来被写成永久的品牌事实。

### 2. 增长方案卡

每个产品可以有多个有版本的阶段性方案。方案卡是轻量化的主目标卡，而不是内容日历。

它必须记录：业务目标、优先人群、核心表达、主战场、候选内容方向、成功标准和暂不做的事。用户可通过专家团对话修改，确认后生成新版本并保留历史。

### 3. 增长实验卡

实验卡是方案卡的子目标。与普通任务不同，它必须是可被结果证伪的假设。

每张卡记录：假设、目标人群、内容母模板、变量、渠道、样本规模、成功指标、停止条件、状态和结果。内容、发布任务与回读数据都挂在对应实验卡上。

### 4. 内容生产台

内容生产台从一张实验卡生成可比较的内容变体。它继承实验的目标人群、平台、内容母模板和成功指标，避免把生成变成脱离目标的无限写稿。

用户或内容 Agent 可以编辑候选内容；进入分发前必须经过所选审核策略。第一版以 X 文本与简单配图为最小能力，不以多平台铺量为前置条件。

### 5. 分发执行台

分发任务明确内容版本、已授权账号、平台形式、计划时间、审核状态和发布回执。它可以在后续将一条内容适配为多平台任务，但所有任务仍属于同一实验卡。

第一版必须支持已授权账号选择、人工审核、定时或即时发布，以及成功或失败的可追溯回执。

### 6. 结果回读与复盘台

结果按内容、实验和方案三个层级汇总。它优先解释目标用户是否行动，而不把播放量误当成增长成功。

可用信号包括平台互动、主页点击、链接归因、注册、首次试用和社媒类计费调用。专家团据此建议保留、放大、修改或停止，并生成下一张实验卡或更新方案。

## 交互形态

用户不需要学习六个独立工具。入口是默认或可选择的“社媒增长专家团”对话：

1. 用户粘贴产品链接，或描述产品与本轮目标。
2. 总协调 Agent 读取业务画像，只追问影响本轮决策的缺失信息。
3. 专家团输出可确认的方案卡与实验卡，而不是只留下聊天记录。
4. 用户在卡片上确认、修改、审核或查看回读；需要时回到同一段对话继续推进。

多 Agent 是内部实现，不是用户面对的一组互相聊天的窗口。总协调 Agent 对当前方案和下一步负责；专项专家只输出结构化诊断、策略、内容或分析建议。

## 与现有 OmniMux 插件的关系

增长专家团应是一个新的垂直插件，暂称 `omnimux-growth`。它拥有自己的增长领域数据，不能把增长方案硬塞进 Hub、账号、资产库或工作流的存储。

| 现有表面 | 角色 | 增长插件如何使用 | 不应承担 |
| --- | --- | --- | --- |
| `omnimux` 执行 Hub | 登录、模型、社媒官方能力和执行 seam | 调用文本、图像、社媒数据和发布能力 | 增长领域存储、第二套 HTTP 客户端或密钥 |
| `omnimux-accounts` | 已授权账号的连接与管理 | 选择可用于分发的账号 | token 存储、账号矩阵复制 |
| `omnimux-assets` | 创作资产和知识素材 | 引用内容制作所需资产 | 保存业务画像、方案或实验真相 |
| `omnimux-workflow` | 通用 DAG 与任务执行 | 后续承接已确认的生产或发布流程 | 第一版的增长判断和卡片管理 |
| `omnimux-analytics` | 产品工具调用埋点 | 衡量产品使用 | 代替社媒效果、点击或转化归因 |

增长插件必须通过 Hub 的 `ctx.get(...)` seam 或 `omnimux_*` 官方工具使用执行能力；不得导入 Hub 内部模块、保存 provider 密钥，或另建 OmniMux HTTP 客户端。插件自身数据应保存于自己的 `$DSH_HOME/omnimux/growth/` 目录，并有明确 schema 与版本。

## 实施顺序

### 第一阶段：增长大脑

实现业务画像、方案卡、实验卡、对话推进和版本历史。此阶段不依赖自动发布，用户已经能获得一轮清晰、可确认的增长实验设计。

### 第二阶段：内容与人工审核执行

从实验卡生成内容候选，连接已授权账号，创建审核后的发布任务并记录回执。执行能力继续复用 Hub 和账号插件。

### 第三阶段：结果学习

将社媒信号、链接归因和产品转化挂回实验卡，生成复盘与下一轮建议。只有这一步完成，产品才对外宣称具备完整的增长闭环。

每一阶段独立可用：第一阶段交付增长判断，第二阶段交付可审核的执行，第三阶段交付可学习的闭环。

## 真实能力与诚实降级

当前社媒数据、账号与发布工具在现有能力清单中仍需真实环境验证。增长插件必须清楚显示“未连接”“待授权”“待验证”或“执行失败”，不得用模拟数据假装已完成闭环。

全链路增长是 OmniMux 的产品北极星，不是对当前已发货功能的夸大承诺。对外表达必须区分已经可靠交付的能力、需要人工审核的环节和未来产品化的判断层。
